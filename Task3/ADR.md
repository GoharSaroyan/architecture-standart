### <a name="_qmphm5d6rvi3"></a>**Решение**

На стрелках обеих диаграмм указаны номера Use Cases (UC1–UC9), которые проходят через эту связь.

#### Суть решения

1. **Ставки переезжают из Excel в АБС.** В АБС появляется модуль ставок и согласования, с которым работают бэк-офисы депозитов и кредитов, каждый в своей роли.
2. **ИБ и АБС общаются только асинхронно через Kafka.** АБС публикует ставки и статусы заявок, ИБ публикует заявки. Прямых вызовов между ними нет.
3. **Депозиты в ИБ — отдельные микросервисы на .NET 8** рядом с существующим монолитом, который не переписывается и остаётся для входа, платежей и текущих счетов.
4. **СМС-код и уведомления делает команда банка** в новых сервисах ИБ через существующий СМС-шлюз, без доработки ядра платформы подрядчика.
5. **Заявки с сайта идут в систему КЦ через Kafka** и попадают в новый модуль-расширение системы КЦ.

#### Диаграмма контекста

На уровне контекста участвуют шесть ролей (потенциальный клиент, клиент ИБ, оператор КЦ, сотрудник отделения, бэк-офисы депозитов и кредитов) и семь систем. Ключевая особенность: **у ИБ и АБС нет прямой связи**, весь обмен идёт через интеграционную шину Kafka (НФТ2). Существующие связи «система КЦ → АБС» (обращение на особые условия) и «АБС → СМС-шлюз» (СМС по обращению) сохраняются без изменений.

**Другие системы**

- **Сайт** (PHP + React.js) получает каталог и ставки и отправляет заявки через API-шлюз ИБ по HTTPS.
- **Система КЦ** получает новый модуль-расширение на Java: он читает `deposit.leads` и `deposit.rates` и показывает оператору заявку вместе с актуальными ставками.
- **СМС-шлюз** используется существующий: его вызывают новые сервисы ИБ и, как и раньше, АБС.

#### Логика принятия решений и выбора технологий

| Решение | Почему так | Требования |
| :- | :- | :- |
| Ставки и их согласование — в АБС | С ними работают бэк-офисы депозитов и кредитов, которые уже работают в АБС; в АБС есть ролевая модель для разделения их данных; АБС развивает своя команда. В задании прямо предложено реализовать это в АБС | F8, F9, НФТ10 |
| Асинхронный обмен ИБ ↔ АБС через Kafka | Требование избегать прямой работы ИБ с АБС; БД АБС перегружена и масштабируется только вертикально; при недоступности АБС заявки ждут в очереди. Kafka рекомендована в задании «на перспективу» и подходит для потоков событий с несколькими получателями | НФТ2, НФТ4, НФТ5, НФТ8 |
| Копия ставок вне АБС, кэш в памяти | Просмотр ставок — самая частая операция; ответ из кэша укладывается в миллисекунды и не нагружает АБС. Ставки меняются редко (раз в день или реже), поэтому копия всегда актуальна. Отдельный кэш-сервер (например, Redis) не нужен: это новая технология без экспертизы в банке | НФТ5, НФТ6, НФТ8, НФТ12 |
| Адаптер АБС на Java | Oracle сам не читает Kafka. Команда АБС знает Java (она уже дорабатывает систему КЦ на Spring Boot). Адаптер изолирует АБС: только он знает о процедурах АБС и сам задаёт темп нагрузки | НФТ2, НФТ8, НФТ12 |
| Новые сервисы ИБ на .NET 8 | Платформа ИБ на .NET Framework 4.5 несовместима с Kafka; .NET 8 совместим, а команда ИБ уже знает C# и .NET. Новые сервисы не зависят от ядра подрядчика, разворачиваются в двух ЦОД и масштабируются горизонтально. Монолит не переписывается: микросервисы только для депозитов, как сказано в задании | НФТ3, НФТ7, НФТ12, НФТ13 |
| Новые БД — MS SQL | MS SQL уже используется в ИБ, команда ИБ умеет с ним работать | НФТ12 |
| Раздел «Депозиты» на React.js | React уже используется на сайте и в системе КЦ; отдельный модуль можно развивать независимо от монолита и сразу сделать по дизайн-системе и требованиям доступности | НФТ12, НФТ14 |
| Outbox и ключ идемпотентности | Событие записывается в БД вместе с данными и отправляется в Kafka отдельно — оно не теряется. Повторная доставка той же заявки распознаётся по ключу и не создаёт второй депозит | НФТ4 |
| Свой сервис СМС-кодов и уведомлений | Доработку ядра ИБ подрядчиком нужно избежать; существующий СМС-шлюз банк уже сопровождает сам | НФТ13 |
| Заявки с сайта — через сервис заявок ИБ | Одна точка приёма всех заявок: единая защита от спама, единая модель заявки, которую можно повторно использовать для кредитов | НФТ11, НФТ15 |
| Расширение системы КЦ, а не доработка ядра | Платформа КЦ расширяема, команда АБС может дорабатывать её на Java без подрядчика | НФТ13 |
| Балансировщик и API-шлюз, два ЦОД | Равномерное распределение запросов между серверами, экземплярами и ЦОД; при сбое одного ЦОД трафик уходит в другой. Kafka тоже развёрнута в двух ЦОД с репликацией | НФТ1, НФТ3, НФТ7 |
| Шифрование | HTTPS (TLS 1.2+) снаружи, TLS между сервисами и для Kafka | НФТ9 |

#### Переход к целевому состоянию (через год)

Решение MVP не придётся переделывать. Чтобы депозиты открывались без бэк-офиса, в АБС автоматизируется шаг подтверждения в UC8: модуль депозитов сам утверждает ставку из справочника и открывает депозит. Остальные контейнеры, топики и сервисы остаются прежними.

|**№**|**Альтернатива**|**Плюсы**|**Почему отклонена**|
| :-: | :- | :- | :- |
|А1|**Синхронная интеграция ИБ с АБС через REST API** (новый API поверх процедур АБС, ИБ вызывает его при показе ставок и подаче заявки)|Проще в реализации, нет новой инфраструктуры (Kafka), клиент сразу видит ответ АБС|Противоречит требованию избегать прямой работы ИБ с API АБС (НФТ2). Каждый просмотр ставок нагружает перегруженную БД АБС (НФТ8); при недоступности АБС ИБ не может ни показать ставки, ни принять заявку (НФТ5); доступность ИБ не может быть выше доступности АБС (НФТ1)|
|А2|**Оставить прямую интеграцию ИБ с БД АБС** (как сейчас для платежей и текущих счетов) и добавить в неё депозиты|Минимум работ: механизм уже существует|Те же недостатки, что у А1, плюс сильная связность: любое изменение схемы БД АБС ломает ИБ. Рост онлайн-заявок напрямую угрожает работоспособности банка (НФТ8)|
|А3|**Реализовать депозиты внутри монолита ИБ** (ASP.NET MVC 4.5) без выделения микросервисов|Не нужно новое окружение и развёртывание; команда ИБ работает в привычном проекте|Платформа ИБ несовместима с Kafka (НФТ12); монолит работает в одном ЦОД на одной группе серверов и не масштабируется горизонтально (НФТ3, НФТ7); изменения в монолите зависят от ядра подрядчика (НФТ13)|
|А4|**Перевести весь интернет-банк на микросервисы сразу**|Единая современная архитектура, нет «двух миров» в ИБ|Слишком большой объём и риск для MVP за 6 месяцев силами 10 человек; в задании прямо сказано — переход на микросервисы «пока только в рамках задачи открытия депозитов»|
|А5|**Ставки в отдельном новом сервисе вне АБС** (например, сервис ставок на .NET с собственной БД и веб-интерфейсом для бэк-офисов)|Не нагружает АБС, легко отдавать ставки в ИБ|Бэк-офисы работают в АБС, пришлось бы дать им второй интерфейс и заново строить ролевую модель для разделения данных депозитов и кредитов (НФТ10). Данные о кредитном риске клиента и так находятся в АБС; согласование заявки и открытие депозита тоже происходят в АБС — разнесение ставок и заявок по разным системам усложнит процесс|
|А6|**Доработать СМС-функционал в ядре платформы ИБ силами подрядчика**|Используется готовый механизм платформы|В задании сказано, что этого лучше избежать (НФТ13): зависимость от сроков и стоимости подрядчика, привязка к обновлениям ядра|
|А7|**Отправлять все СМС из АБС** (АБС уже умеет отправлять СМС по обращениям из КЦ)|Не нужен сервис уведомлений в ИБ|Добавляет нагрузку на АБС (НФТ8); СМС-код для подтверждения заявки в ИБ нельзя отправлять из АБС без синхронного обращения к ней (НФТ2)|
|А8|**Другая очередь сообщений: RabbitMQ / IBM MQ** или обмен через общие таблицы БД|RabbitMQ проще в эксплуатации; обмен через таблицы не требует новой инфраструктуры|Банк рекомендует Kafka «на перспективу» (НФТ12). Kafka хранит историю событий и позволяет подключать новых получателей (например, систему КЦ, а позже — партнёрский КЦ) без изменения источника. Обмен через общие таблицы снова связывает системы через БД|
|А9|**Заявки с сайта напрямую в систему КЦ** (сайт вызывает API системы КЦ)|Меньше звеньев в цепочке|Два разных входа для заявок с разной защитой и разной моделью данных; модель заявки нельзя будет повторно использовать для кредитов (НФТ11, НФТ15); сайт будет зависеть от доступности системы КЦ|
|А10|**Отдельный распределённый кэш (Redis)** для ставок|Общий кэш для всех экземпляров сервиса|Новая технология без экспертизы в банке (НФТ12). Ставки меняются редко, объём данных небольшой — кэша в памяти каждого экземпляра с копией в MS SQL достаточно|

**Недостатки, ограничения, риски**

**Недостатки**

|**№**|**Недостаток**|**Как смягчаем**|
| :-: | :- | :- |
|Н1|**Новая инфраструктура.** Kafka, API-шлюз и окружение для .NET 8-сервисов в двух ЦОД нужно развернуть и сопровождать; опыта эксплуатации Kafka в банке нет|Начать с минимального кластера Kafka (3 брокера на ЦОД), обучение команды инфраструктуры, мониторинг с первого дня (НФТ15)|
|Н2|**Итоговая согласованность (eventual consistency).** Копия ставок в ИБ обновляется с небольшой задержкой после изменения в АБС; статус заявки в ИБ появляется не мгновенно|Ставки меняются раз в день или реже — задержка в секунды некритична. При подаче заявки ставка фиксируется вместе с версией справочника; АБС проверяет актуальность и при расхождении предлагает новую ставку через статус|
|Н3|**Сложнее отладка.** Заявка проходит через 5–7 контейнеров и Kafka — найти, где она «застряла», сложнее, чем в монолите|Сквозной идентификатор заявки во всех событиях и логах, централизованная трассировка, мониторинг отставания потребителей Kafka|
|Н4|**«Два мира» в ИБ.** Часть ИБ — монолит на .NET Framework 4.5, часть — микросервисы на .NET 8; две модели разработки и развёртывания|Чёткая граница: монолит отвечает только за вход и встраивание раздела «Депозиты». Новый функционал (кредиты) — только в новой части|
|Н5|**Нагрузка на команду АБС.** На неё приходится больше всего работ: модуль ставок, доработка модуля депозитов и клиента, адаптер на Java, расширение системы КЦ|Приоритизация: сначала ставки и адаптер (без них ничего не работает), расширение КЦ — позже; при необходимости — временное усиление Java-разработчиками|
|Н6|**Клиент не получает ответ сразу.** В MVP заявку обрабатывает человек, депозит открывается не мгновенно|Это осознанное ограничение MVP. Статус заявки в ИБ и СМС снижают число звонков в КЦ; в целевом состоянии подтверждение в АБС автоматизируется|

**Ограничения**

|**№**|**Ограничение**|
| :-: | :- |
|О1|Требования доступности 99,9% и работы при сбое ЦОД выполняются **только для новых сервисов депозитов**. Монолит ИБ по-прежнему работает в одном ЦОД; если он недоступен, клиент не может войти в ИБ и, значит, не попадёт в раздел «Депозиты». Полная доступность ИБ — отдельный проект|
|О2|**АБС масштабируется только вертикально.** Адаптер защищает её от всплесков, но пропускная способность обработки заявок ограничена возможностями АБС и числом сотрудников бэк-офиса|
|О3|**Новый клиент не может открыть депозит онлайн**: с сайта подаётся только заявка, для открытия нужна личная идентификация в отделении (требование законодательства)|
|О4|**Особые условия по заявке с сайта** согласуются через существующую интеграцию КЦ → АБС и существующую отправку СМС из АБС: в MVP этот путь не переводится на Kafka|
|О5|Изменения в **системе КЦ** ограничены механизмами расширения платформы подрядчика; объём доработки нужно подтвердить с подрядчиком|
|О6|**Целевые значения** (≤ 300 мс, ×10 нагрузки, RTO ≤ 15 мин) предложены архитектором и требуют согласования с бизнесом; под них нужно провести нагрузочное тестирование|

**Риски**

|**№**|**Риск**|**Вероятность / влияние**|**Меры**|
| :-: | :- | :- | :- |
|Р1|**Доработки АБС (Oracle, PL/SQL) дополнительно нагрузят перегруженную БД**: новые таблицы, Outbox, расчёт персональных предложений|Средняя / высокое|Расчёт персональных предложений — ночным пакетом; чтение Outbox — небольшими порциями; ограничение скорости в адаптере; нагрузочное тестирование АБС до запуска|
|Р2|**Команда не успеет освоить Kafka и .NET 8** за срок MVP|Средняя / среднее|Обучение в начале проекта, пилот на одном потоке (`deposit.rates`) до остальных; .NET 8 близок к знакомому команде C#|
|Р3|**Подрядчик платформы ИБ ограничит встраивание** нового раздела или выдачу токена в монолите|Низкая / высокое|Заранее согласовать с подрядчиком точки расширения монолита; запасной вариант — раздел «Депозиты» как отдельное приложение с переходом из ИБ по ссылке с токеном|

|Р5|**Расхождение ставок**: клиент видит в ИБ или на сайте одну ставку, а в АБС уже другая|Низкая / высокое|Единый источник — АБС; публикация при каждом изменении; версия ставки в заявке и проверка в АБС (см. Н2)|
|Р6|**Потеря или дублирование заявки** при сбоях Kafka или сервисов|Низкая / высокое|Outbox в источниках, ключ идемпотентности, репликация Kafka между ЦОД, мониторинг «зависших» заявок|
|Р7|**Утечка персональных данных** при передаче через новые звенья (шлюз, Kafka, логи)|Низкая / высокое|TLS на всех соединениях, разграничение доступа к топикам, маскирование персональных данных в логах, хранение только в контуре банка|
|Р8|**Спам-заявки с сайта** создают ложную нагрузку на кол-центр|Средняя / среднее|Ограничение частоты в API-шлюзе, проверка номера телефона, фильтрация повторов в сервисе заявок|
