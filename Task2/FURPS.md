# FURPS+: онлайн-заявка на депозит (MVP)

Область: подача заявки на депозит / накопительный счёт на сайте и в интернет-банке (ИБ), обработка заявки бэк-офисом в АБС, СМС-уведомления клиента.

В колонке «Комментарий» указан источник требования (п. N — пункт описания в задании 2, «Ландшафт» — блок «IT-ландшафт компании», «Задание 1» — процесс открытия депозита). Требования, добавленные дополнительно, отмечены **Доп.**, для них приведено обоснование.

| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| F   | Функциональные (Functionality)     |              |
| F1  | Сайт показывает список доступных депозитов и накопительных счетов с актуальными ставками | п. 1. Ставки должны браться из единого источника (см. F8), а не вноситься вручную, иначе ставка на сайте разойдётся со ставкой в АБС |
| F2  | На сайте новый клиент подаёт заявку на депозит, указав Ф. И. О. и номер телефона, без регистрации | п. 1 |
| F3  | Заявка с сайта автоматически попадает в систему кол-центра; менеджер КЦ видит её, звонит клиенту и может предложить особые условия | п. 1. Система КЦ — платформа подрядчика с возможностью расширения; доработку может выполнить команда АБС (Java) |
| F4  | Согласованные с клиентом условия по заявке с сайта доступны сотруднику отделения в АБС при визите клиента для идентификации | п. 1. Новый клиент обязан пройти личную идентификацию; сотрудник фронт-офиса не должен заново запрашивать ставку у бэк-офиса по почте (Задание 1, п. 3) |
| F5  | ИБ показывает клиенту список депозитов и накопительных счетов с актуальными ставками и персонализированные ставки лично для него | п. 2 |
| F6  | В ИБ клиент подаёт заявку на открытие депозита / накопительного счёта, указав счёт списания и сумму | п. 2. Цель через 6 месяцев — депозит **и** накопительный счёт в ИБ |
| F7  | Подача заявки в ИБ подтверждается одноразовым СМС-кодом | п. 2. Реализуется командой банка вне ядра платформы ИБ (см. +R4) |
| F8  | Ставки по депозитам (базовые и персонализированные) ведутся в АБС вместо XLS-файлов; с ними работают сотрудники бэк-офиса депозитов и бэк-офиса кредитов | п. 2, Задание 1. Ставки не хранятся ни в одной системе, это главный барьер для онлайн-продаж |
| F9  | Процесс согласования ставки по заявке, в том числе специальной, реализован в АБС: бэк-офис кредитов передаёт оценку кредитного риска, бэк-офис депозитов утверждает ставку, без почты и Excel | п. 2, Задание 1, п. 4–5. С учётом разграничения доступа (см. +R5) |
| F10 | На этапе MVP онлайн-заявку обрабатывает менеджер бэк-офиса: подтверждает условия депозита в АБС | п. 4 |
| F11 | Клиент получает СМС-уведомление после подтверждения размера ставки и после открытия депозита | п. 4. Отправка через существующий СМС-шлюз |
| F12 | Клиент видит в ИБ статус своей заявки: подана → ставка подтверждена → депозит открыт / отклонена | **Доп.** В MVP заявку обрабатывает человек, это может занять часы. Без статуса клиенты, в основном пожилые, будут звонить в КЦ, а его нагрузка и так растёт |
| F13 | Журнал аудита: кто и когда создал заявку, изменил ставку, подтвердил условия | **Доп.** Банковская деятельность требует прослеживаемости операций; ставка влияет на финансовый результат банка и на условия договора с клиентом |
| U   | Удобство использования (Usability) |              |
| U1  | Интерфейсы сайта и ИБ выполнены по принятой в банке дизайн-системе: привычные цвета и брендированные элементы | п. 5 |
| U2  | Форма заявки на сайте минимальна: Ф. И. О., телефон, согласие на обработку персональных данных | п. 1. Согласие — **Доп.**, обязательно по закону о персональных данных (см. +R7) |
| U3  | Интерфейсы соответствуют требованиям доступности (WCAG 2.1, уровень AA): крупный шрифт, контрастность, понятные формулировки | **Доп.** Основная аудитория банка — люди старшего возраста, маркетинговая кампания будет направлена и на них |
| U4  | Адаптивная вёрстка сайта и ИБ для мобильных устройств | **Доп.** Цель трансформации — привлечь молодых клиентов, которые пользуются в основном смартфоном |
| R   | Надёжность (Reliability)           |              |
| R1  | Сервисы нового процесса работают 24/7 с доступностью не ниже 99,9% (не более ≈ 8 ч 45 мин простоя в год) | п. 6 |
| R2  | ИБ не обращается напрямую к API и БД АБС в новом процессе; обмен идёт асинхронно через промежуточный слой (очередь сообщений) | п. 6. Сбой или перегрузка АБС не должны останавливать ИБ, а поток онлайн-заявок не должен перегружать БД АБС. Сейчас ИБ интегрирован напрямую с БД АБС — это нужно изменить для нового процесса |
| R3  | Новые сервисы ИБ развёрнуты в основном и резервном ЦОД; при сбое ЦОД они остаются доступны и выдерживают требуемую нагрузку | п. 6. Команда ИБ считает это пока невыполнимым для текущего монолита (одна группа серверов), поэтому требование относится к новым сервисам депозитов. Это риск, который нужно отразить в ADR |
| R4  | Заявки и уведомления не теряются: если АБС недоступна, заявка сохраняется и обрабатывается после восстановления, повторная доставка не создаёт дубликатов | **Доп.** Прямое следствие R2: при асинхронном обмене нужны гарантированная доставка и идемпотентная обработка, иначе клиент может открыть два депозита или не получить ответа |
| R5  | При недоступности АБС ИБ и сайт продолжают показывать ставки и принимать заявки | **Доп.** Следствие R1 и R2: ставки читаются из копии вне АБС, а не из АБС при каждом запросе |
| R6  | Целевые RTO ≤ 15 минут и RPO = 0 для принятых заявок (значения согласовать с бизнесом) | **Доп.** 99,9% без явных RTO и RPO не проверить; потеря поданной заявки означает потерю клиента и денег |
| P   | Производительность (Performance)   |              |
| P1  | Время отклика операций интерфейса — миллисекунды: ориентир ≤ 300 мс для 95% запросов | п. 5. В задании цель не оцифрована, значение предложено для проверки и согласования с бизнесом |
| P2  | Справочные данные (ставки, список продуктов, справочники для платежей) загружаются быстрее, чем сейчас (сейчас дольше 1 с): кэшируются на стороне ИБ | п. 5 |
| P3  | Новые сервисы ИБ масштабируются горизонтально; запросы равномерно распределяются между серверами, экземплярами приложений и ЦОД | п. 6 |
| P4  | Нагрузка на АБС не растёт пропорционально числу онлайн-клиентов: чтение ставок и продуктов идёт не из АБС, запись заявок дозируется (ограничение скорости) | п. 6. АБС масштабируется только вертикально, её БД уже перегружена |
| P5  | Система рассчитана на кратный рост числа пользователей ИБ после запуска маркетинговой кампании (ориентир — ×10 от текущего, уточнить у бизнеса) | **Доп.** Сейчас клиентов в ИБ мало, но цель проекта — их привлечь; без целевой нагрузки нельзя спланировать масштабирование |
| S   | Поддерживаемость (Supportability)  |              |
| S1  | Разрабатывается документация для дальнейшего расширения: архитектура (C4, ADR) и контракты API / событий (OpenAPI, AsyncAPI) | п. 3 |
| S2  | Функциональность депозитов в ИБ выносится в отдельные микросервисы, которые не зависят от ядра платформы подрядчика | п. 3. Обновление ядра ИБ привязано к подрядчику; отдельные сервисы банк развивает сам. Перевод на микросервисы — только в рамках депозитов |
| S3  | Модель заявки и процесс согласования не привязаны к депозитам: их можно повторно использовать для кредитов | **Доп.** Следующий этап плана бизнеса — заявки на кредит в ИБ и на сайте |
| S4  | Централизованный мониторинг, логирование и трассировка запросов через ИБ, очередь, АБС и систему КЦ | **Доп.** Без мониторинга нельзя подтвердить 99,9% и быстро найти сбой в распределённом процессе |
| S5  | Доработки распределены по командам банка: ИБ — команда ИБ, АБС и расширение системы КЦ — команда АБС (есть Java-экспертиза), сайт — собственная разработка | п. 2, п. 3, Ландшафт. Минимизирует зависимость от подрядчиков |
| +R  | + Ограничения (Restrictions)       |              |
| +R1 | Весь трафик с персональными данными шифруется: HTTPS (TLS 1.2+) на сайте и в ИБ, шифрование при обмене между системами | п. 1, п. 2 |
| +R2 | Используются технологии, уже есть в банке: MS SQL, Oracle, .NET, Java, PHP / React.js. Новые технологии должны быть совместимы с ними, и в банке должна быть экспертиза хотя бы на уровне языка | п. 3 |
| +R3 | Очередь сообщений — Kafka. Текущая платформа ИБ (.NET Framework 4.5) с Kafka несовместима, поэтому интеграцию с Kafka делают новые сервисы на современном .NET | п. 3. Сохраняет экспертизу команды ИБ в .NET |
| +R4 | Ядро платформы ИБ (функционал СМС) не дорабатывается силами подрядчика; СМС-код и уведомления реализует команда банка | п. 2 |
| +R5 | Сотрудники бэк-офиса депозитов и бэк-офиса кредитов не имеют доступа к данным друг друга: ролевая модель доступа в АБС | Задание 1, п. 5. Требование безопасности |
| +R6 | Новый клиент не может открыть депозит без личной идентификации в отделении | п. 1. Требование законодательства |
| +R7 | Обработка персональных данных — по законодательству о персональных данных: согласие клиента, хранение в контуре банка, маскирование в логах | **Доп.** С сайта передаются Ф. И. О. и телефон, в ИБ — данные счетов |
| +R8 | Форма заявки на сайте защищена от автоматических и повторных отправок (ограничение частоты, проверка номера телефона) | **Доп.** Публичная форма без регистрации — источник спама, который создаёт ложную нагрузку на КЦ |
| +R9 | Система КЦ — платформа подрядчика: доработки только через предусмотренные механизмы расширения, без изменения ядра | Ландшафт |
| +R10 | Сроки: MVP — 6 месяцев (заявка онлайн, обработка бэк-офисом); целевое состояние — 12 месяцев (автоматическое открытие без бэк-офиса) | Цели бизнеса. Решение MVP не должно мешать переходу к целевому состоянию |
