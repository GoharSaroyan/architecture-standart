## Задание 1. Карта IT-ландшафта и схема интеграции приложений

### Цель

Определить, что сейчас мешает сделать депозиты и накопительные счета полностью цифровым продуктом, доступным в интернет-банке.

### Исходные данные

**Business Capability Map** (бизнес-возможности второго уровня):

| Продажи и маркетинг | Поддержка операционных процессов |
|---|---|
| Продажи в сети отделений | Обслуживание депозитных процессов |
| Продажи через кол-центр | Обслуживание кредитных процессов |
| Digital-оповещения клиентов | Управление договорами |

**Организационная структура** (7 направлений):

| Направление | Роль | Численность |
|---|---|---|
| Управление обслуживанием в сети отделений | фронт-офис | 50 отделений, 500 чел. |
| Управление IT | интернет-банк, АБС | ИБ: 10 + 10 подрядчик; АБС: 20 |
| Управление обслуживанием депозитных продуктов | бэк-офис | 50 |
| Управление обслуживанием кредитных продуктов | бэк-офис | 50 |
| Кол-центр банка | операторы | 200; поддержка подрядчика: 5 |
| Партнёрский кол-центр | внешняя компания | 100 |
| Команда цифровой трансформации розничного бизнеса | развитие онлайн-каналов | 10 |

**IT-системы:** АБС (Delphi + Oracle, логика на PL/SQL), интернет-банк (ASP.NET MVC 4.5, MS SQL, платформа подрядчика, интеграция напрямую с БД АБС), система кол-центра (платформа подрядчика: React, Java Spring Boot, PostgreSQL), система партнёрского кол-центра (внешняя), СМС-шлюз и телеком-оператор, сайт (PHP + React). Ставки по депозитам считаются в Excel и рассылаются по почте.

**Выводы: что мешает сделать депозит цифровым продуктом**

1. **Ставки по депозитам не ведутся ни в одной системе.** Их считают в Excel на основе ставки рефинансирования ЦБ и уровня кредитного риска и ежедневно рассылают по почте. Без ставок в системе интернет-банк не может показать их клиенту.
2. **Согласование ставки идёт по почте.** Цепочка «фронт-офис → бэк-офис депозитов → кредиты → обратно» существует из-за требования безопасности: сотрудники депозитов и кредитов не должны видеть данные друг друга. Отсюда ожидание клиента от 20 минут до часа.
3. **Онлайн-каналы не участвуют в депозитных процессах.** Интернет-банк умеет только платежи и открытие текущих счетов, сайт показывает только маркетинговую информацию. В BCM нет возможности «онлайн-продажи».
4. **Обращения из кол-центра обрабатываются в АБС вручную.** Партнёрский кол-центр не интегрирован с банком и работает по переданным скриптам.

### 1.2. Схема интеграции приложений

Файл: [Task1/integration-scheme.drawio](Task1/integration-scheme.drawio), изображение: [Task1/integration-scheme.png](Task1/integration-scheme.png)

**Что показано:** приложения банка, внешние системы и участники процесса открытия депозита в текущем состоянии (As-Is) и все потоки данных между ними. Потоки пронумерованы (1–15) и расшифрованы в таблице на схеме.

| Обозначение | Значение |
|---|---|
| тёмно-синий блок | участник процесса (клиент, сотрудники) |
| синий блок | приложение банка (сайт, интернет-банк, АБС, система КЦ, СМС-шлюз) |
| серый блок | внешний участник или система (партнёрский КЦ, телеком-оператор, ЦБ) |
| розовый пунктирный блок | ручной обмен: электронная почта и Excel |
| синяя стрелка | автоматическая интеграция |
| **красная стрелка** | проблемная интеграция — прямой доступ интернет-банка к БД АБС |
| красная пунктирная стрелка | ручная передача данных |
| серая стрелка | работа пользователя с системой, звонок |

**Основные потоки:**

| № | Участники | Что передаётся |
|---|---|---|
| 1–2 | Клиент → сайт, интернет-банк | маркетинговая информация; платежи и текущие счета, депозитов нет |
| 3 | Интернет-банк → БД АБС | **прямая интеграция с БД Oracle** |
| 4–5 | Клиент → оператор КЦ → система КЦ → АБС | обращение о депозите для предварительного расчёта ставки |
| 6 | АБС → СМС-шлюз → телеком-оператор → клиент | СМС о ставке и приглашение в отделение |
| 7–8 | ЦБ → бэк-офис кредитов → почта/Excel | ежедневный расчёт ставок вручную и рассылка в бэк-офис депозитов |
| 9–10 | Отделение ↔ почта ↔ бэк-офис депозитов ↔ бэк-офис кредитов | запрос ставки и данных о кредитном риске для специальной ставки |
| 11–13 | Бэк-офисы и отделение → АБС | обработка обращений, анализ риска, создание депозита и загрузка документов |
| 14–15 | Бизнес → партнёрский КЦ; клиент → оператор партнёра | скрипты звонков вне IT-систем; консультация без актуальных ставок |

**Что видно на схеме:**

1. **Половина потоков по ставкам — ручные** (7–10): Excel и почта связывают ЦБ, бэк-офис кредитов, бэк-офис депозитов и отделения. Пока ставки не ведутся в системе, интернет-банк не может их показать.
2. **Интернет-банк работает с БД АБС напрямую** (3). Если добавить депозиты через эту же интеграцию, растёт нагрузка на перегруженную БД и связность систем — поэтому в MVP (задание 3) обмен переводится на асинхронный.
3. **Интернет-банк и сайт не участвуют в депозитном процессе**: от них нет потоков к процессу расчёта ставки и открытия депозита.
4. **Партнёрский КЦ не интегрирован** (14–15): он получает только скрипты и не знает актуальных ставок — это решается в задании 4.

## Задание 2. FURPS+ таблица

Файл: [Task2/FURPS.md](Task2/FURPS.md)

### Что сделано

Требования из описания MVP (подача заявки на депозит на сайте и в интернет-банке) разложены по группам FURPS+:

| Группа | Что в неё вошло |
|---|---|
| **F** — функциональные | что умеют сайт, интернет-банк, система КЦ и АБС: ставки, заявки, СМС-код, согласование ставки, уведомления |
| **U** — удобство | дизайн-система банка, минимальная форма, доступность для пожилых клиентов |
| **R** — надёжность | 99,9% 24/7, отказ от прямой работы ИБ с АБС, резервный ЦОД, гарантированная доставка заявок |
| **P** — производительность | отклик в миллисекундах, кэш справочников, горизонтальное масштабирование, защита АБС от нагрузки |
| **S** — поддерживаемость | документация, микросервисы вне ядра подрядчика, расширяемость под кредиты, мониторинг |
| **+R** — ограничения | шифрование, существующие технологии, Kafka, запрет доработки ядра ИБ, разграничение доступа, законодательство |

### Как выбирались архитектурно-значимые требования

В таблицу попали только требования, которые влияют на архитектуру: выбор систем, интеграций, способа обмена, развёртывания и разграничения ответственности команд. Например, «ставки хранятся в АБС» определяет, где живут данные, а «ИБ не работает с API АБС напрямую» — способ интеграции через очередь.

Для каждого требования указан источник. Дополнительные требования (**Доп.**) добавлены там, где без них исходные требования нельзя выполнить или проверить: статус заявки, аудит, доступность для пожилых, гарантированная доставка, RTO/RPO, целевая нагрузка, мониторинг, персональные данные, защита формы от спама.

### Ключевые противоречия, которые нужно решить в архитектуре (Задание 3)

1. **99,9% и резервный ЦОД против текущего монолита ИБ** на одной группе серверов → новые сервисы депозитов выносятся из монолита и разворачиваются в двух ЦОД.
2. **Kafka против .NET Framework 4.5** → интеграцию с Kafka делают новые сервисы на современном .NET.
3. **Рост онлайн-заявок против перегруженной БД АБС**, которая масштабируется только вертикально → асинхронный обмен, копия ставок вне АБС, дозирование записи.
4. **СМС-код нужен, но ядро ИБ дорабатывать нельзя** → отдельный сервис СМС-кодов от команды банка через существующий СМС-шлюз.

### Ключевые решения

1. **Ставки — в АБС.** Новый модуль ставок и согласования заменяет Excel и почту; бэк-офисы депозитов и кредитов работают в нём в разных ролях.
2. **ИБ ↔ АБС — только через Kafka.** АБС публикует ставки и статусы, ИБ — заявки. Адаптер АБС на Java забирает заявки с ограничением скорости и защищает перегруженную БД.
3. **Депозиты в ИБ — новые микросервисы на .NET 8** рядом с существующим монолитом: продукты и ставки, заявки, СМС-коды, уведомления. Монолит не переписывается.
4. **СМС-код и уведомления — силами банка** через существующий СМС-шлюз, без доработки ядра подрядчика.
5. **Заявки с сайта → сервис заявок ИБ → Kafka → расширение системы КЦ.**

### Как устроен ADR

- **Use Cases (UC1–UC9)** покрывают ведение ставок, сайт, кол-центр, отделение, интернет-банк и уведомления. Номера UC подписаны на стрелках диаграмм — видно, что диаграммы покрывают все сценарии.
- **Нефункциональные требования (НФТ1–НФТ15)** отобраны из FURPS+ таблицы задания 2 и ссылаются на исходные коды.
- **Решение**: описание каждого контейнера и топика Kafka, логика выбора технологий, путь каждого UC по контейнерам, участие команд, переход к целевому состоянию через год.
- **Альтернативы (А1–А10)**: плюсы и причина отказа для каждой.
- **Недостатки (Н1–Н6), ограничения (О1–О6), риски (Р1–Р8)** — с мерами по смягчению.

### Какие команды участвуют

| Команда | Основные работы |

| Команда сайта | каталог ставок и форма заявки |
| Подрядчик ИБ | не участвует |

### Суть решения

Ставки уже ведутся в модуле ставок АБС и публикуются в Kafka (топик `deposit.rates`) в рамках MVP из задания 3. К этому потоку добавляются **два новых получателя** без изменения источника:

1. **Кол-центр банка** — модуль-расширение системы КЦ получает ставки из Kafka, хранит копию и показывает оператору панель «Ставки по депозитам».
2. **Партнёрский кол-центр** — новый сервис выгрузки ставок формирует CSV-файл с полным снимком ставок (при каждом изменении и ежедневно в 08:00) и кладёт его на SFTP-сервер банка в DMZ; партнёр забирает файл сам по SSH-ключу со своих IP-адресов.

Нагрузка на АБС не растёт, ставки во всех каналах совпадают, партнёр не получает доступа во внутреннюю сеть банка.

### Как устроен ADR

- **Use Cases (UC1–UC8)**: путь ставки от бэк-офиса до операторов обоих КЦ и контроль доставки.
- **Функциональные (ФТ1–ФТ12) и нефункциональные (НФТ1–НФТ14) требования** — только для нового кейса; требования MVP из задания 3 продолжают действовать.
- **Диаграммы** показывают только то, что участвует в передаче ставок (интернет-банк и сайт не изображены).
- **Решение**: компоненты, формат файла для партнёра, логика выбора технологий, участие команд.
- **Альтернативы (А1–А12)** по трём вопросам: как получает ставки КЦ банка, как — партнёр, где формировать файл.
- **Недостатки (Н1–Н5), ограничения (О1–О6), риски (Р1–Р7)** — с мерами.

### Последовательность работ (RoadMap)

| Веха | Когда | Что к ней готово |
|---|---|---|
| Ставки в АБС и Kafka | конец М3 | модуль ставок АБС, Outbox, публикация `deposit.rates`, Kafka в двух ЦОД |
| Ставки в КЦ банка и у партнёра | конец М5 | панель ставок в системе КЦ, SFTP в DMZ, сервис выгрузки, забор файлов партнёром, мониторинг |
| Запуск MVP | конец М6 | сервисы депозитов в ИБ, сайт, обработка заявок в АБС, пилот |
| Старт маркетинговой кампании | М7 | только после готовности онлайн-каналов и обоих кол-центров |
| Целевое состояние | конец М12 | автоматическое открытие депозитов без бэк-офиса (ИБ и отделение), персональные ставки для оператора |
