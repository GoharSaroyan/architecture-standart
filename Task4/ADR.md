### <a name="_b7urdng99y53"></a>**Название задачи:** Передача актуальных депозитных ставок в кол-центр банка и партнёрский кол-центр (MVP)

### <a name="_3bfxc9a45514"></a>**Функциональные требования**

**Контекст.** Основная аудитория банка — люди старшего возраста. После запуска маркетинговой кампании ожидается рост звонков с вопросами об условиях депозитов. Операторы собственного кол-центра (КЦ) и партнёрского КЦ должны консультировать клиентов по актуальным ставкам. Решение строится на процессе работы со ставками из MVP ([Task3/ADR.md](../Task3/ADR.md)): ставки ведутся в модуле ставок АБС и публикуются в Kafka (топик `deposit.rates`).

Сокращения: КЦ — кол-центр, АБС — автоматизированная банковская система, DMZ — демилитаризованная зона сети банка.

|НФТ1|**Без нагрузки на АБС.** Передача ставок в КЦ банка и партнёрский КЦ не создаёт новых запросов к АБС и её БД: используется уже существующая публикация ставок в Kafka. (Задание 3, НФТ2, НФТ8)|

|НФТ13|**Технологии и команды.** Используются технологии, уже принятые в банке: Kafka, Java / Spring Boot (опыт есть у команды АБС), PostgreSQL системы КЦ. Система КЦ дорабатывается только через механизмы расширения платформы, без изменения ядра подрядчика.|
|НФТ14|**Расширяемость.** Формат файла документирован (описание колонок, кодировка, разделитель, правила именования) и версионируется; подключение ещё одного партнёра не требует изменения сервиса выгрузки — только новой папки и настроек доступа.|

На диаграммах показано только то, что участвует в передаче ставок; интернет-банк, сайт и сервисы заявок из MVP не изображены. На стрелках указаны номера Use Cases (UC1–UC8).

#### Суть решения

Ставки уже ведутся в модуле ставок АБС и публикуются в Kafka (топик `deposit.rates`) в рамках MVP. Решение добавляет к этому потоку **двух новых получателей**, не меняя источник:

1. **КЦ банка** — модуль-расширение системы КЦ подписывается на `deposit.rates`, хранит копию ставок и показывает её оператору в панели «Ставки по депозитам».
2. **Партнёрский КЦ** — новый сервис выгрузки ставок подписывается на `deposit.rates`, формирует CSV-файл с полным снимком ставок и кладёт его на SFTP-сервер банка в DMZ, откуда партнёр забирает файл сам.

#### Диаграмма контекста

Поток ставок идёт в одну сторону: бэк-офис депозитов → АБС → Kafka → (система КЦ банка | сервис выгрузки → SFTP-сервер ← система партнёрского КЦ). От АБС выходит одна связь — та же, что и в MVP, поэтому нагрузка на АБС не растёт (НФТ1). Обе связи с SFTP-сервером направлены к нему: банк не обращается в систему партнёра, а партнёр не попадает во внутреннюю сеть банка (НФТ6, НФТ7). Система мониторинга контролирует выгрузку, забор файла и актуальность ставок в КЦ и оповещает дежурного IT (НФТ12).

#### Диаграмма компонентов

**Сервис выгрузки ставок** (новый; Java 17, Spring Boot; разрабатывает команда АБС)

| Компонент | Технология | Назначение | UC | ФТ / НФТ |
| :- | :- | :- | :- | :- |
| Получатель ставок | Spring Kafka | Читает `deposit.rates`, сохраняет последний снимок ставок в БД выгрузок и запускает формирование файла | UC4 | ФТ1, ФТ7, НФТ1 |
| Планировщик | Spring Scheduler | Ежедневно в 08:00 запускает формирование файла, даже если ставки не менялись | UC5 | ФТ7, НФТ3 |
| API администрирования | Spring Web, REST | Ручной повторный запуск выгрузки дежурным IT; доступ только из внутренней сети | UC8 | ФТ10 |
| Формирователь файла | Java, Apache Commons CSV | Формирует CSV (UTF-8) с полным снимком ставок по документированной версии формата и файл контрольной суммы SHA-256 | UC4, UC5 | ФТ5, ФТ6, НФТ2, НФТ10, НФТ14 |

#### Формат файла для партнёра

| Параметр | Значение |
| :- | :- |
| Имя файла | `deposit_rates_ГГГГММДД_ЧЧММСС.csv` и `deposit_rates_ГГГГММДД_ЧЧММСС.csv.sha256` |
| Кодировка, разделитель | UTF-8, точка с запятой (`;`), первая строка — заголовки |
| Колонки | `format_version`; `product_code`; `product_name`; `product_type` (депозит / накопительный счёт); `term_days`; `amount_from`; `amount_to`; `currency`; `rate_percent`; `valid_from` |
| Содержание | Полный снимок всех действующих базовых ставок, без персональных данных |
| Порядок выкладки | Сначала CSV, затем `.sha256`; партнёр забирает CSV только после появления файла контрольной суммы — так он не прочитает недописанный файл |

Описание формата передаётся партнёру как отдельный документ и версионируется (`format_version`) (НФТ14).

#### Логика принятия решений и выбора технологий

| Решение | Почему так | Требования |
| :- | :- | :- |
| Источник ставок — модуль ставок АБС, канал — существующий топик `deposit.rates` | Условие требует решения «на основе текущего процесса работы со ставками». Новые получатели подключаются к Kafka без изменения источника — АБС не получает ни одного нового запроса, ставки во всех каналах совпадают | ФТ1, НФТ1, НФТ2 |
| КЦ банка получает ставки напрямую из Kafka | Система КЦ — на Java Spring Boot, клиент Kafka для неё стандартен; модуль-расширение для заявок с сайта уже появляется в MVP — ставки добавляются в тот же модуль. Копия в БД КЦ позволяет работать при недоступности АБС и Kafka | ФТ2, ФТ3, НФТ4, НФТ13 |
| Только базовые ставки для оператора | Условие требует консультаций «хотя бы по текущим ставкам». Показ персональных ставок требует идентификации клиента по телефону — отдельная задача безопасности, вне MVP | ФТ4 |
| Отдельный сервис выгрузки, а не логика в АБС или системе КЦ | Формирование файлов — новая ответственность, не связанная ни с учётом в АБС, ни с работой оператора. Отдельный сервис не нагружает АБС, не зависит от платформы подрядчика КЦ и может обслуживать других партнёров | НФТ1, НФТ13, НФТ14 |
| Java 17, Spring Boot | Опыт есть у команды АБС; та же технология, что у адаптера АБС из MVP и у системы КЦ | НФТ13 |
| PostgreSQL для БД выгрузок | Уже используется в банке (система КЦ); для снимка ставок и журнала достаточно небольшой БД | НФТ13 |
| Полный снимок, а не изменения | Партнёру не нужно собирать ставки из нескольких файлов; потеря одного файла не приводит к ошибке — следующий файл снова полный | НФТ2, НФТ5 |
| Выгрузка при изменении + ежедневно в 08:00 | Изменения доходят до партнёра в течение минут; утренний файл гарантирует актуальные ставки к началу смены, даже если какой-то файл не был забран | ФТ7, НФТ3 |
| CSV (UTF-8) | Простой открытый формат: читается любой системой и вручную в Excel, к которому привыкли сотрудники. Не требует от партнёра специальных библиотек | ФТ5 |
| SFTP-сервер банка в DMZ, партнёр забирает файлы сам | Партнёр не может вызывать API и готов работать с файлами. Сервер в DMZ отделяет внешнего участника от внутренней сети; банк контролирует сервер и по журналу видит, забран ли файл | ФТ8, НФТ6–НФТ8 |
| SSH-ключи, белый список IP, раздельные права | Исключает подбор пароля и доступ с чужих адресов; партнёр не может изменить или удалить файлы банка | НФТ8 |
| SHA-256 и порядок выкладки | Партнёр проверяет целостность и не читает файл, который ещё записывается | ФТ6, НФТ10 |
| Мониторинг и ручной перезапуск | Устаревшая ставка у партнёра — репутационный риск; о сбое должен узнать дежурный IT, а не клиент | ФТ10, ФТ11, НФТ12 |

#### Участие команд

| Команда / сторона | Работы |
| :- | :- |
| Команда АБС | Модуль ставок в АБС и публикация в `deposit.rates` (из MVP); сервис выгрузки ставок; модуль «Ставки по депозитам» в системе КЦ |
| Управление IT, инфраструктура | SFTP-сервер в DMZ, сетевые правила, ключи и белый список, правила мониторинга |
| Подрядчик системы КЦ | Консультирует по механизму расширения платформы |
| Партнёрский КЦ | Настраивает забор файлов по SFTP, проверку SHA-256 и загрузку ставок в свою систему |
| Бизнес (бэк-офис депозитов, команда цифровой трансформации) | Правила, какие ставки можно сообщать по телефону; обновлённые скрипты звонков для партнёра; приёмка |

#### Переход к целевому состоянию (через год)

Решение не требует переделки. В целевом состоянии оператору КЦ банка можно показывать персональные ставки клиента (после идентификации по телефону) — для этого модуль «Ставки по депозитам» дополнительно подписывается на топик `deposit.offers` из MVP. Если партнёр в будущем сможет принимать данные по API, сервис выгрузки дополняется новым способом отправки без изменения источника ставок.

**Как КЦ банка получает ставки**

|**№**|**Альтернатива**|**Плюсы**|**Почему отклонена**|
| :-: | :- | :- | :- |
|А1|**Система КЦ запрашивает ставки у АБС** через существующую интеграцию КЦ → АБС или новый API АБС при каждом открытии панели|Ставки всегда «из первых рук», не нужен получатель Kafka в системе КЦ|Добавляет запросы к перегруженной АБС при каждом звонке (НФТ1); при недоступности АБС операторы остаются без ставок (НФТ4); противоречит принципу MVP «обмен с АБС только через Kafka»|
|А2|**Система КЦ берёт ставки из сервиса продуктов и ставок интернет-банка** по REST|Сервис уже существует в MVP, ставки там уже в кэше|Создаёт зависимость КЦ от доступности интернет-банка; сервис ИБ спроектирован для клиентов ИБ и сайта, а не для внутренних систем. Kafka уже доставляет те же данные напрямую|
|А3|**Ставки в КЦ вносятся вручную** (бэк-офис рассылает Excel-файл или оператор смотрит ставки на сайте банка)|Не нужна разработка|Возвращает ручной процесс, от которого уходит MVP; риск устаревших и ошибочных ставок (НФТ2, НФТ3); для сайта — оператор видит только то, что видит любой посетитель, без дат начала действия|

**Как партнёрский КЦ получает ставки**

|**№**|**Альтернатива**|**Плюсы**|**Почему отклонена**|
| :-: | :- | :- | :- |
|А4|**API для партнёра** (REST или Kafka-топик, открытый партнёру)|Мгновенная доставка, нет файлов|Партнёр не может делать API-вызовы — прямое условие задания (НФТ6)|
|А5|**Банк выкладывает файлы на SFTP-сервер партнёра**|Банку не нужен свой SFTP-сервер|Требует исходящего соединения из банка во внешнюю систему и хранения учётных данных партнёра в банке; банк не видит, загрузил ли партнёр файл в свою систему; зависимость от доступности и настроек сервера партнёра. При своём сервере в DMZ банк полностью контролирует точку обмена (НФТ7, НФТ11)|
|А6|**Отправка файла по электронной почте**|Просто, не нужна инфраструктура|Ненадёжно (спам-фильтры, ограничения размера), нет гарантии и контроля доставки, сложно автоматизировать загрузку у партнёра; почта как канал передачи — ровно то, от чего уходит банк (Задание 1)|
|А7|**Передача только изменений ставок (дельта)**, а не полного снимка|Меньше объём файла|Партнёру нужно собирать актуальное состояние из цепочки файлов; потеря одного файла приводит к неверным ставкам. Объём полного снимка ставок мал (десятки строк), экономия незначительна (НФТ2, НФТ5)|
|А8|**Формат XLSX или XML/JSON вместо CSV**|XLSX привычен бизнесу; XML/JSON поддерживают вложенную структуру и схему|XLSX — бинарный формат, сложнее для автоматической загрузки и проверки; XML/JSON избыточны для плоской таблицы ставок. CSV читается любой системой и при необходимости открывается в Excel|
|А9|**Выгрузка только по расписанию** (раз в день) или **только при изменении**|Проще логика сервиса|Только по расписанию — изменения ставок днём доходят до партнёра на следующий день (НФТ3). Только при изменении — если файл потерялся, партнёр работает с устаревшими ставками до следующего изменения (НФТ5). Комбинация закрывает оба случая|

**Недостатки, ограничения, риски**

**Недостатки**

|**№**|**Недостаток**|**Как смягчаем**|
| :-: | :- | :- |
|Н1|**Задержка у партнёра.** Партнёр получает ставки не мгновенно, а когда его система заберёт файл; между изменением ставки и обновлением у партнёра проходят минуты (в худшем случае — до следующего забора файла)|Ставки меняются редко; в каждом файле указана дата начала действия (`valid_from`), поэтому новую ставку можно выложить заранее. Согласовать с партнёром частоту забора файла (например, раз в 15 минут)|
|Н2|**Новые элементы для сопровождения**: сервис выгрузки, его БД, SFTP-сервер в DMZ, правила мониторинга|Сервис небольшой, на той же технологии, что адаптер АБС из MVP; SFTP — стандартный компонент инфраструктуры; сопровождение закрепляется за командой АБС и инфраструктурой|
|Н3|**Банк не контролирует систему партнёра**: по журналу SFTP видно, что файл скачан, но не видно, загружен ли он в систему партнёра и видят ли его операторы|Закрепить в соглашении с партнёром регламент загрузки и контроль на его стороне; периодическая проверка контрольными звонками бизнесом банка|
|Н4|**Две копии ставок вне АБС** (в БД системы КЦ и в БД выгрузок) в дополнение к копии в интернет-банке из MVP|Все копии обновляются из одного топика и содержат полный снимок; источник истины один — АБС; мониторинг отслеживает время последнего обновления|
|Н5|**Ещё одна доработка платформы подрядчика КЦ** — модуль-расширение становится больше (заявки с сайта + ставки)|Использовать только официальные механизмы расширения; согласовать объём с подрядчиком заранее; при обновлении платформы проверять модуль регрессионными тестами|

**Ограничения**

|**№**|**Ограничение**|
| :-: | :- |
|О1|Операторы обоих КЦ видят **только базовые ставки**; персональные ставки клиента в MVP не показываются. Особые условия по-прежнему согласуются через обращение в АБС (процесс MVP)|
|О2|Решение работает только после запуска **модуля ставок АБС и топика `deposit.rates`** из MVP. До этого момента ставки вне Excel не существуют — передавать нечего|
|О3|Партнёр получает данные **только файлами по SFTP**; оперативные изменения доходят до него с задержкой, равной интервалу забора файла|
|О4|Доступ к SFTP-серверу возможен **только с заранее согласованных IP-адресов** партнёра; при смене адресов или ключей у партнёра нужна заявка в IT банка|
|О5|Целевые значения (1 минута до системы КЦ, 5 минут до файла, 08:00, хранение файлов 30 дней, журнала 1 год) предложены архитектором и требуют согласования с бизнесом и службой информационной безопасности|
|О6|Скрипты звонков для партнёра передаются **организационно**, вне IT-систем, как и сейчас; их актуальность обеспечивает бизнес|

**Риски**

|**№**|**Риск**|**Вероятность / влияние**|**Меры**|
| :-: | :- | :- | :- |
|Р1|**Партнёр консультирует по устаревшим ставкам** (не забрал файл, не загрузил в свою систему, сбой выгрузки)|Средняя / высокое|Ежедневный полный файл в 08:00; мониторинг забора файла с оповещением; ручной перезапуск выгрузки; регламент с партнёром; в скрипте — фраза о том, что точные условия фиксируются при оформлении|
|Р2|**Задержка запуска модуля ставок АБС** из MVP задерживает и передачу ставок в КЦ|Средняя / высокое|Модуль ставок — первая задача в RoadMap. Временный вариант: бэк-офис публикует ставки в `deposit.rates` через простую форму загрузки, пока модуль не готов|
|Р3|**Подрядчик КЦ не поддержит** нужный механизм расширения или обновление платформы сломает модуль|Низкая / среднее|Согласовать механизм расширения до начала разработки; регрессионные тесты модуля при каждом обновлении платформы|
|Р4|**Компрометация доступа к SFTP** (утечка ключа партнёра)|Низкая / среднее|В файлах только публичные ставки, персональных данных нет; белый список IP; доступ только на чтение; регулярная смена ключей; журнал подключений|
|Р5|**Партнёр неверно разберёт файл** (кодировка, разделитель, формат чисел)|Средняя / среднее|Документированный формат с примером; тестовая папка и тестовые файлы до запуска; совместные испытания с партнёром|
|Р6|**Нагрузка на КЦ всё равно превысит возможности** обоих кол-центров после маркетинговой кампании|Средняя / среднее|Запускать кампанию поэтапно; мониторить очередь звонков; подсказки и статус заявки в интернет-банке (MVP) снижают число звонков|
|Р7|**Расхождение ставок между каналами** (оператор назвал одну ставку, в ИБ клиент видит другую)|Низкая / высокое|Единый источник — АБС; все каналы получают полный снимок из одного топика; дата начала действия в каждой ставке|
